# 阶段 B 实现：正面经验与可复用做法

来源：[阶段 B #185](https://github.com/MeteoBoy4/PaperRadar/issues/185) 的实施、人工核查、故障修复与收口过程。本篇保存一次复盘，供后续任务按需引用；现行执行规则仍以任务授权、项目 Agent 指引和 Contract 为准。

适用场景：一个 spec 同时包含可并行的代码开发、访问可变数据的真实执行、人工判断，以及需要固定版本的验收。纯代码小改动可只采用相关部分。

## 1. 用两类任务处理两种并发边界

阶段 B 按标签区分代码票与人工会期票：代码票使用独立 worktree；真实票操作同一个实验根，由主会话串行执行。会期按业务闸门组织，而不是每完成一张票就机械中断。

可复用步骤：

1. 在派工前按 tracker 标签确认任务类型，读取完整原生依赖关系。
2. 为代码票分配独立工作树；派工时声明是否新增 migration，并明确共享 head 的串行依赖。
3. 真实会期开始前确认全部 blockers 的提交已在集成分支上。Issue 关闭只表示 tracker 状态，不能替代提交可达性检查。
4. 优先合齐当次会期所需代码，再启动单写者会期。

完成判据：每张票的执行者、代码来源、共享资源和进入条件明确；真实根没有并发写者。

复用价值：并行发生在可隔离的代码工作上，真实数据的先后关系保持可追溯。原生任务图与共享资源规则见[固定范围与集成](../../docs/agents/verification-scope.md)。

## 2. 把真实执行固定在一个代码版本上

本次在提取修复和恢复修复后，都结束旧执行，再从新 SHA 开始新执行。原失败及其运行材料保留，新的结果有自己的代码身份。

可复用步骤：

1. 使用专用 checkout，开始时记录完整 HEAD，并将其写入运行回执。
2. 会期内保持 checkout 不 merge、不 rebase、不切换版本。
3. 发现需要代码修复时，先记录已完成动作、失败步骤和已消耗的 attempt，再结束该次执行。
4. 修复合入后，记录新 SHA、创建新回执，只执行获授权的恢复范围。

完成判据：每份结果都能回答“哪个代码版本、哪个输入、哪次执行产生”；更换代码不覆盖旧结论。

实例：[#204 版式验收](../../docs/verification/issue-204-live-layout-acceptance.md)和[#205 恢复验收](../../docs/verification/issue-205-recovery-acceptance.md)分别绑定其执行提交。

## 3. 让人工核查绑定具体制品，并保留否决

人工核查发现了页眉混入正文章节、尾部标题层级失真，以及内联科学符号缺少受限标记等问题。这说明人工质量闸门承担了机器检查之外的实际职责。

可复用步骤：

1. 为待核查制品生成可定位的材料入口，明确样本、版本和指纹。
2. 将问题拆成可独立回答的判据，要求逐项结论；只有回答对象清楚时，才接受“全部通过”的合并表达。
3. 将用户指出的位置与症状交给工程修复，保留旧制品和原否决。
4. 新提取或新版本重新执行全部适用核查，不继承旧制品的局部通过项。
5. 若由 Agent 代录，保留 owner 的原答及所对应的对象；推进命令本身不替代质量签收。

完成判据：人工结论可以追溯到具体制品；旧否决仍可查，新通过没有跨版本继承。

实例：[#204 六项核查结论](../../docs/verification/issue-204-live-layout-acceptance.md)。该结论仅覆盖冻结样本，不能外推为通用提取质量。

## 4. 用 fresh 工程上下文修复真实执行暴露的问题

本次将现场问题转成有边界的工程任务，再由 fresh implementer 修复；代码开发与真实执行的权限边界保持分离。

可复用派工模板：

> 目标：修复已确认症状，并说明根因与影响范围。先声明是否新增 Alembic migration。
> 不得执行任何真实/live 命令；不得创建、读取或修改实验根；不得读取凭据。
> 测试使用临时合成根、已确认的 HTTP/Pi/Docling 替身及注入时钟。
> 先复现预期失败，再修复；回报提交、验证结果、未验证项和详细证据路径。

复现材料必须来自允许使用的合成输入或明确授权的脱敏信息，不能让工程代理自行搜寻私有材料。真实登录由用户操作，Agent 仅按授权核对元数据。

完成判据：开发回归能独立解释修复；工程代理不需要访问真实根或凭据，真实重启由会期执行者另行处理。

实例：[r1/r2 逐项处置与合成回归](issue-185-stage-b-review-r1-r2-disposition.md)、[离线门禁失败后的定向诊断](issue-185-offline-gate-followup.md)。fresh 上下文有助于明确任务边界，其质量仍由实际复现和独立验证保证。

## 5. 按故障边界恢复，复用已验证的上游成果

真实 Read、报告和备份已成功，隔离 replay 后续失败。本次修复后仅重新回放已有已验证备份，没有重新调用模型或生成业务 attempt。

可复用步骤：

1. 分开列出成功步骤、失败步骤、尚未执行步骤；耗时推断与已确诊原因分开表述。
2. 核对成功产物的身份和校验结果，判断哪些能作为恢复输入。
3. 向 owner 提供具体恢复范围及其影响；按明确授权执行。
4. 校验恢复输出与固定输入的一致性，同时核对新增业务动作数量。

完成判据：恢复只重复必要步骤，保留原失败记录；产物一致性和隔离要求均有实际验证。

实例：[#205 恢复验收](../../docs/verification/issue-205-recovery-acceptance.md)记录了新增模型调用和业务 attempt 均为零。原失败的确切成因仍作为未验证项保留，没有用后续成功倒推旧故障原因。

## 6. 审阅建议逐项裁决，以可验证风险决定修改范围

本次对两份外部报告逐项判断：修复有行为风险的发现，采纳必要的小接口改进，对收益不明确、扩大关键修改面的框架重构给出拒绝理由。

可复用步骤：

1. 保留原审查报告，逐项列出判断、依据和处置。
2. 对行为缺陷先复现；对原本已正确的行为如实补回归，不声称修前失败。
3. 选择能覆盖实际风险的最小完整修复；拒绝项说明不同生命周期、异常责任或历史兼容等具体理由。
4. 由单一 fresh implementer 处理同轮相互关联的修复，再独立核验。

完成判据：每条建议都有明确去向；接受项有验证，拒绝项有可审阅依据，原报告保持可追溯。

实例：[r1/r2 处置表](issue-185-stage-b-review-r1-r2-disposition.md)。这种做法保留审阅价值，同时避免把审查意见自动扩大为全局重构授权。

## 7. 保护历史字节，让新版本承担新行为

章节展示修复引入 renderer v2，并通过线性 migration 扩展允许的版本；旧 renderer v1 的固定输入、报告与历史回放继续保持。后续迁移测试使用真实旧 revision 的合成历史夹具，而不是在新格式数据上制造不合法的旧状态。

可复用步骤：

1. 先识别变更是否影响持久化约束、固定投影或历史重建。
2. 需要新版本时显式演进，并保留旧版本读取与重建路径。
3. 用有明确身份的非空历史夹具验证升级、恢复和字节一致性。
4. 对无法保留历史语义的降级明确拒绝；涉及表定义或 migration 时运行 Schema 一致性测试。

完成判据：新行为有新版本身份，旧历史仍能按原语义验证，非法迁移得到预期拒绝。

实例：[renderer 迁移与兼容处置](issue-185-stage-b-review-r1-r2-disposition.md)、[历史夹具与拒降边界](issue-185-offline-gate-followup.md)。

## 8. 分开记录工程、真实链和恢复的证明范围

本次公开签收分别保存版式、真实链和恢复结论，包含哈希、计数与未验证项；私有材料和运行细节留在私有回执。代码审查和离线测试不会替真实行为签收。

可复用步骤：

1. 先明确当前结论证明的是代码行为、特定样本的真实执行，还是恢复过程。
2. 分别记录代码身份、材料身份、实际数量、owner 结论和未验证项。
3. 公开材料只保留允许披露的内容，通过摘要关联私有回执。
4. 查询正式门禁时同时核对历史结果与当前适用性；代码或文档变化后的旧通过不能称为当前树通过。

完成判据：读者能确定每条结论的对象和边界，未验证项不会因为其他层面通过而消失。

实例：[#204 版式](../../docs/verification/issue-204-live-layout-acceptance.md)、[#205 真实链](../../docs/verification/issue-205-live-chain-acceptance.md)、[#205 恢复](../../docs/verification/issue-205-recovery-acceptance.md)。正式门禁身份规则见[固定范围与集成](../../docs/agents/verification-scope.md)。

## 在下一次任务中使用

可在任务说明中引用本篇，并指定需要复用的章节：

> 参考阶段 B 正面经验，采用代码／真实执行分流、固定 SHA 会期、制品级人工签收、fresh 合成修复和分层证据。先核对本任务授权与现行规则，列明本次适用项；每个阶段以对应完成判据结束。

使用时只带入与当前任务有关的步骤。真实运行路径、凭据状态、具体 SHA、测试数量和用户授权都需要按本次执行重新确定。

本篇不把尚未实现的改进列为成功经验：版本消费者检查与本地自动触发分别由 [#207](https://github.com/MeteoBoy4/PaperRadar/issues/207) 和 [#208](https://github.com/MeteoBoy4/PaperRadar/issues/208) 承接；专用 HITL 执行会话与结构化交接协议仍是建议。门禁前完成文档维护已有现行规则，本次门禁后维护导致适用性变化，是后续应避免的返工，见[文档维护记录](issue-185-document-maintenance.md)。
