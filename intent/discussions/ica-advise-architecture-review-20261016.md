# 候选 01：配置材料共同规则 · 第一轮只覆盖七类 YAML（选 A）

## 决策是什么

候选 01（把配置材料的共同规则集中到一个模块，当前装载与历史回放共用）分几轮落地。Q2 问第一轮范围：

- A：只覆盖七类 YAML 配置（Profile、模型、主题、期刊、复用升级、正文提取、Read）；
- B：同时统一提示词（prompt）、冻结契约（contract schema/manifest）和 Pi 适配器（adapter）材料。

**选定 A。** 第一轮只收七类 YAML 配置的重复规则；prompt、契约、adapter 留待模式验证后的后续轮次，接口设计不得排除它们日后加入。

## 为什么

- 重复确实集中在七类 YAML：装载路径 `service.py:167-265` 是七个调用 `_versioned_yaml_material` 的同构块；回放路径 `service.py:352-437` 是七个几乎逐字相同的 elif 分支（`validate_yaml_bytes` → 版本对 settings → 编译值对 entry），唯一变体是 Extraction 的 `compiled_config()`。审视报告引用的同步修改证据（提交 e86d3b9 新增期刊）也全部落在这条路径上。
- 其余三类材料形状本质不同：prompt 是 Markdown 文本、版本在文件名里、无内部版本字段、编译值是 `{"text": ...}`；冻结契约是不可变权威字节、带漂移检测和专属错误指引表（`_CONTRACT_CHECK_GUIDANCE`）；adapter 已经有自己的共用模块 `adapter_loading.py`（正是报告说的"现有共用规则的参考"），且与系统提示词有 sha256 跨材料绑定、受 ADR-0026 约束。第一轮就强行统一四种形状，容易做出错误抽象。
- 范围小则风险小：快照身份固定测试、各类 `*_persistence` 跨进程回放测试可以精确钉住行为；ADR-0023（快照与校准基线分开）与 ADR-0026 边界不动。
- A 不排斥 B：后续轮次可以在新模式验证后吸收 prompt（必要时契约）。实现注意：新模块的公共接口不要把"七类"硬编码到无法扩展的位置。

## 是否改变外部行为

否。两条路径（当前装载、历史回放）产出的快照身份、材料登记键、错误语义、CLI 输出均保持不变；`compiled_config()` 的特殊语义保留；纯编译仍不依赖 YAML、数据库或 CLI。

## 是否需要 ADR

否。纯内部模块组织与实施节奏选择，不改变领域不变量、公共契约或版本语义；ADR-0023/0026 的既有边界继续遵守。若后续轮次决定吸收 prompt/契约/adapter，届时再评估。

## 实施方案确认（2026-10-16，同 session）

实施方给出的方案与决策一致，已确认按此实施：两条读取路径各司其职（当前文件读取、历史回放验证已存记录完整性）；一个模块统一七类 YAML 的版本核对、齐全性检查与"配置对象＋材料记录"配对组装，调用方不再分别拼装；Models 的类型化访问（供模型协议校验读取）与 Extraction 的 `compiled_config()` 特殊语义保留；prompt、冻结契约、Pi 材料沿用现有处理。验证锚点与方案声明一致，均为现有真实测试：`test_synthetic_example_has_fixed_snapshot_identity`（固定快照身份）、`test_profile_snapshot_survives_source_removal_and_new_process` / `test_cross_process_load_uses_database_only`（删源后跨进程回放）、`test_load_rejects_damaged_version_content`（损坏拒绝）、`test_mid_transaction_failure_leaves_no_config_facts`（事务回滚）、各 `*_persistence` 测试（真实子进程）及 `./scripts/check-offline`。

附注（已转达实施方）：新模块的公共接口不要把"七类"硬编码到无法扩展的位置，为后续轮次吸收 prompt（必要时契约）留出空间；快照身份与中文错误消息文本须逐字节不变。

# 候选 02：离线验收 · 只集中编排与结论发布，不动底层执行与进度记录（选 A）

日期：2026-10-16
状态：已决。
来源：同报告候选 02；grilling Q2（是否同时整理底层的执行与进度记录）。

## 决策是什么

候选 02（一次离线验收的执行与收尾由一个模块负责，共用不可覆盖的结论发布步骤）的改造深度：

- A：新模块集中整体编排（安排检查、协调中断）和三份结论的统一发布；现有执行器 `offline_evidence.py` 继续负责启动检查子进程与运行中进度更新，pytest 回执插件 `a2_test_receipt.py` 继续记录实际测试执行。
- B：连检查进程管理、运行中证据写入、pytest 回执写入一起调整，范围扩大到整条证据生成流程。

**选定 A。**

## 为什么

- 重复确实只在上层：三处结论发布（`a1_acceptance.py:394` 附近、`a2_acceptance.py:233` 附近、`a2_full_acceptance.py:414` 附近）是同一套"临时文件＋fsync＋硬链接发布、目标存在即失败"的逐字重复；编排与中断处理在 `run_a1_verification` / `run_full_verification` / `write_full_a2_conclusion` 间分担。这正是候选 02 陈述的痛点。
- 底层没有重复可收：执行器（`_run_checks` + `_write_evidence`）和回执插件各自已是单一模块，职责集中。B 只是追求形式统一，不消除任何重复，违背审视报告自己的删除检验标准。
- 两种写入语义必须分开：运行中证据用 `os.replace` 原子替换（允许更新），已发布结论用 `os.link` 硬链接发布（不可覆盖）。报告的边界注记明说"不能混成同一种写入"；A 在结构上保留了这条边界，B 会把它们卷进同一条流水线。
- 风险面：证据文件字段语义与回执格式是 `docs/verification/offline-evidence.md` 记载的公开格式，且被真实子进程测试用独立字面量断言钉住（生产者与消费者有意不共享判定）；固定范围哈希（`a1_scope.py` / `a2_full_scope.py`）覆盖这些脚本。B 触及这些区域的收益最小、验证成本最高。git 历史显示这些文件只在验收需求本身演进时一起改（#12→#13→#25），无日常漂移痛点。

## 是否改变外部行为

否。A1／A2-01／完整 A2 三份结论的文件名、格式、不可覆盖语义、终端中文输出与入口退出码（仅本次 A1 与完整 A2 均通过才返回 0）保持不变；运行中证据与 pytest 回执的写入方式完全不动。

## 是否需要 ADR

否。验收脚本的内部组织选择，不改变 `docs/verification/offline-evidence.md` 记载的证据/结论格式或任何领域不变量。实施时同步更新固定范围哈希并复核行为未变（不可仅更新哈希掩盖行为变化）。

## 实施方案确认（2026-10-16，同 session）

实施方给出的方案与选 A 一致，已确认按此实施：新模块统一组织一次运行（检查计划只执行一次、协调中断、按明确顺序发布各组结论）；验收组显式登记（名称、输出文件、判定入口、是否影响整体通过），组织代码不写死只有 A1 和 A2，未来新组可接入自己的范围与判定；执行顺序与通过条件分开（A2-01 先发布但整体仍由 A1 与完整 A2 决定）；共用原子写入＋禁止覆盖的发布步骤；旧入口、中文输出、证据格式与中断语义兼容。

核实过的关键声明：`a2_test_receipt.py` 确实只登记 `a1_scope` + `a2_full_scope` 两套固定模块（"当前回执只覆盖 A1 与完整 A2"属实，本轮不动它符合范围）；`a2_full_acceptance.py` 先发布 A2-01 再发布完整 A2 且不继承前者通过状态，返回码只看 A1 与完整 A2，与文档一致。合成扩展验收组仅存在于测试中（假检查进程），不触碰真实验收范围；`test_a2_full_entry` / `test_a2_full_acceptance` 的既有锚点（一次计划四文件绑定、中断、不可覆盖、证据替换、固定文件漂移）继续作为验收依据。
