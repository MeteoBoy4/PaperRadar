# 「直接人工决定」在 §7.5 允许来源表中缺失 denied 原因

状态：已确认并落地（2026-09-21）。采用方案 A，三个 denied 原因全部对「直接人工决定」开放。`intent/draft.md` §7.5 已按本结论同步；权威枚举生成源与 `contracts/screening/decision-reasons-v1.schema.json` 尚未实现，由 Issue #8 / #9 按本结论交付。

触发问题：`intent/draft.md` §7.5 的决定原因表把「普通复核」和「直接人工决定」列为两个来源，但三个 denied 原因只列了「普通复核」而没有「直接人工决定」；同时 §8.1 的 `screening set-decision` 又要求 `denied` 必须提供 `--reason`。按现有文字，直接人工决定无法合法地写出一个 denied。

参照文件：

- `intent/draft.md` §7.5（决定与处理原因，含权威原因表）、§8.1（必备 CLI 清单）、§4.11（报告与复核）、§4.5（条件式复用升级）
- `CONTEXT.md`「普通复核」「pending」「denied」词条
- 契约导出目标：`contracts/screening/decision-reasons-v1.schema.json`
- 相关讨论：`intent/archived_discussions/claude-advise-grill.md` 第 25 条（建议建立「原因枚举 × 允许来源」权威表）

## 一、问题描述

§7.5 开头的纪律是：**原因枚举由代码中的一份权威定义导出到 `contracts/screening/decision-reasons-v1.schema.json`；每个值限制允许的结果和来源，各处不得维护字符串副本。** 因此该表的「允许来源」列是决定事件 `source` 取值的白名单，必须完整覆盖所有合法写入路径。

表中涉及人工来源的行如下（**修改前**的 §7.5 表，`intent/draft.md`）：

|原因|结果|允许来源|
|---|---|---|
|out_of_scope|denied|建议规则、盲评、普通复核|
|low_value|denied|建议规则、盲评、普通复核|
|low_reuse_feasibility|denied|建议规则、盲评、普通复核|
|user_judgment|accepted|盲评、普通复核、直接人工决定|
|unclear_from_available_input|pending|盲评、普通复核、直接人工决定|
|defer_judgment|pending|盲评、普通复核、直接人工决定|
|outside_current_focus|pending|盲评、普通复核、直接人工决定|

即：accepted / pending 的四个原因同时允许「普通复核」和「直接人工决定」，但 denied 的三个原因只允许「普通复核」。表中没有任何一行把 `直接人工决定` 与 denied 结果关联起来。

## 二、上下文：两个来源的定义与差异

按 §4.11 与 `CONTEXT.md`，两者是同一类人工筛选决定的**不同入口**，而不是不同的决定语义：

- **普通复核**（`intent/draft.md:696–704`、`CONTEXT.md:208–210`）：依据普通日报固定编号 `N1`–`N5`（只含其中当前仍 pending 的条目）或复核队列 `review queue`，通过 `review submit --report` / `review submit --queue` 批量提交。非盲、不生成 reveal、不重新计算历史报告成员、可积压。
- **直接人工决定**（`intent/draft.md:1092`、`:704`）：逐篇 `paper-radar screening set-decision <paper-id> <accepted|pending|denied> --reason ...`，§4.11 明说它「仍作为直接入口」，不依赖任何日报槽位；典型场景是用户跳过了某天日报、论文不再出现在任何新日报（`intent/archived_discussions/claude-advise-grill.md` 第 25 条给出原因表的设计建议，第 14 条讨论复核积压缺少列表与批量提交入口的背景），或 `reuse_escalation_unavailable` 时用户「直接作人工决定」（`intent/draft.md:432`）。
- 两者共同点：都写 `screening_decision_events`；都是人工决定，优先级高于系统建议（§3.7）；都非盲；在校准隔离期对 `waiting_calibration` / 未揭晓批次论文同样被拒绝（§4.5、§8.2）。
- 表中用户可见的 denied 原因语义为：`out_of_scope`（超出范围）、`low_value`（研究价值低）、`low_reuse_feasibility`（复用可行性低）；`insufficient_metadata` 属于元数据人工放弃，`manual_read_request` 属于人工精读请求，均不在本文范围。

## 三、冲突点

把 §7.5 表与 §8.1 命令定义直接对照：

1. §8.1 的 `screening set-decision <paper-id> <accepted|pending|denied> --reason ...` 只有一个 `--reason` 参数，且三态都接受。命令本身不区分「这次 denied 来自普通复核还是直接入口」。
2. §7.5 规定 `denied` 必须带受控原因，且原因必须由权威枚举导出。
3. 但对 `denied` 结果，枚举白名单不包含 `直接人工决定` 这个来源。

按字面实现会产生两种都不理想的结果：要么直接人工决定做 denied 时因来源不在白名单而被拒绝（功能缺口，违反「逐篇 `screening set-decision` 仍作为直接入口」），要么实现者自行放宽白名单——正是 §7.5 开头的「不得各自维护字符串副本」与 AGENTS.md「受控 enum / reason」所要防止的分叉。

对照 §7.5 表内其他行可以确认这不像是「有意限制入口」：accepted / pending 行都显式并列了 `直接人工决定`，说明作者确实把两个入口当作不同 `source` 值处理；denied 行只列 `普通复核`，更可能是重写时漏列。

## 四、影响面

- 只影响 `screening_decision_events` 的 `source` 白名单与 `contracts/screening/decision-reasons-v1.schema.json` 的校验规则。
- 不影响建议规则（`建议规则` 行不变）、不影响 `模型失败`/`元数据人工放弃`/`人工精读请求` 三类来源。
- 不影响阶段输入指纹、校准语义、Read 门禁或报告投影；若最终选择在 denied 行补上 `直接人工决定`，不触发 calibration change workflow，也不需要新 ADR。

## 五、候选方案

**方案 A（推荐）：在三个 denied 行补上「直接人工决定」。**

- 即 `out_of_scope` / `low_value` / `low_reuse_feasibility` 的允许来源改为「建议规则、盲评、普通复核、直接人工决定」。
- 理由：与 §8.1 `set-decision ... denied --reason` 对齐，与同表 accepted / pending 行对两个入口的并列处理保持一致，且符合「原因与入口解耦」的现有设计。
- 代价：需同步更新权威枚举定义与其 `contracts/` 冻结导出；无行为语义变化。

**方案 B：在 §8.1 明确直接人工决定不接受 `denied`。**

- 即规定 `screening set-decision` 只能做 accepted / pending，denied 必须通过普通复核入口提交。
- 代价：与 §4.11「逐篇 `screening set-decision` 仍作为直接入口」和 §4.5「用户可以…直接作人工决定」的措辞冲突；并且会削弱跳过日报后的积压处理能力（这些论文可能永远不在任何新日报里）。不推荐。

**方案 C：保持现状但在 §7.5 旁注说明。**

- 即在表中显式写明「denied 只能来自建议规则 / 盲评 / 普通复核，直接入口不写 denied」，把现状固定为有意决策。
- 代价：需要同时修改 §8.1 与 §4.11 的相关措辞，否则仍是文档间矛盾。只有在确认「直接入口确实不能 denied」时采用。

## 六、确认结论

选择 **方案 A**：允许 `screening set-decision ... denied --reason` 作为直接人工决定，并将 `out_of_scope`、`low_value`、`low_reuse_feasibility` 三个 denied 原因全部对该来源开放。

确认理由：

1. **来源与原因应当正交。**「直接人工决定」和「普通复核」记录的是决定从哪个交互入口写入；`out_of_scope` / `low_value` / `low_reuse_feasibility` 记录的是用户为什么作出 denied。交互入口不应改变同一个人工判断的业务语义。
2. **三个原因都有合法的直接决定场景。**用户可以直接确认论文超出研究边界、研究价值不足，或基于自身数据、工具和现实约束判断复用可行性低。这些判断不需要先经由日报或复核队列才成立。
3. **限制 denied 来源会损害审计质量。**如果同一决定仅因进入路径不同就不允许记录真实原因，用户可能被迫绕道进入复核队列、暂时误标为 pending，或选择不准确的原因。这会使持久化事实取决于 UI 路径，而不是业务语义。

保留以下边界：

- denied 仍只允许上述三个受控人工原因，不为 denied 增加泛化的 `user_judgment`；具体原因对审计和后续分析仍有价值。
- 直接入口仍必须遵守校准隔离规则；对 `waiting_calibration` 或未揭晓批次中的论文，普通 `screening set-decision` 仍应拒绝执行，不能借方案 A 绕过盲评隔离。
- 这是对已有产品语义矛盾的收口，不改变建议规则、阶段指纹、Read 门禁或校准语义，因此不触发 calibration change workflow，也不需要新 ADR。但实现上仍是对「来源 × 结果 × 原因」校验白名单的放宽，除权威枚举与冻结契约外，应同步覆盖 CLI 校验和组合测试。

后续落地：`intent/draft.md` §7.5 已按方案 A 修改表格，并在表后补充「普通复核与直接人工决定只记录入口、不改变原因」的解耦说明；§8.1 命令清单无需改动。
