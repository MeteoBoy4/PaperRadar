# 路线图维护

**粒度**：一个模块 = 一张可以由 to-spec → to-tickets → implement-spec 执行的 spec issue。票级任务图、领取与进行中状态只在 GitHub 原生关系中维护；路线图只链接 spec issue。

**状态集合**：

- 主流程：未成形 → 待裁决／待探索 → 可规格化 → 已规格化（链接 spec issue）→ 已完成。
- 另有「已取消」，保留一行写明原因。
- 「当前前沿」= 依赖全部已完成的「可规格化」模块，加上所有「已规格化」模块；与模块表在同一次更新中维护。
- 状态只在模块表维护；当前前沿、待探索、已完成等板块引用模块表，不写票号或票范围的时点快照。
- 模块图只表达依赖与是否完成，不复述模块表的主流程状态；状态以模块表为准。

**节点 ID** 保持稳定，不复用。

**承接责任**按下游模块汇总在模块承接索引，条目引用冻结收口表的 I/T/D 编号；原文措辞与下一责任节点以该表为准，只写前向信息，不写回顾叙述。

**待裁决表**的字段：编号、问题、阻塞的模块、最迟闸门、裁决后应写入的位置。需要长讨论时开 issue，表中只留链接。

**待探索表**的字段：编号、问题、阻塞的模块、解决方式（research／live 探测／原型）。

**排期与责任**：

- 不写日历排期；先后用依赖与闸门表达，例如「最迟 X 前」。
- 执行方式标 AFK 或 HITL；需要用户裁决或提供的事项单独标出。

**篇幅**以 Agent 单次会话能整份读完为准。已完成模块折叠为一行：spec issue 链接 + 验收证据链接。

**更新时机**：

- to-spec 发布后，把模块改为「已规格化」并附链接。
- implement-spec 收尾时，在模块表（图）中标记完成，在「已完成」板块补上该模块行，并把实现中发现、需要下游处理的缺口写成下游模块的承接责任（附出处）。
- 待裁决或待探索项关闭时，结论写入规格或 ADR，路线图删除该项并更新依赖。
- 板块分两类：活状态板块随发布、收尾与裁决关闭更新；历史冻结板块（「Read 恢复证据范围」至「证据定位标签」一批）只由文档统一类变更迁移，不随日常发布或收尾更新。

**skill**：`.agents/skills/` 下的 vendored skill 不修改。项目流程以本文件为准，由 AGENTS.md 引用。
