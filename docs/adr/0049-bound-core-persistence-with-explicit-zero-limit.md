# 用项目显式零 core 限额约束 Apport 持久化

状态：已接受；日期：2026-11-07；依据：#167 所有者 H4-core 终局裁决；补充 [ADR-0039](0039-isolate-pi-with-landlock.md) 与 [ADR-0046](0046-consolidate-pi-readiness-under-live.md)。

普通exec会重置pre-exec的dumpable设置；全机core分发链超出项目可推定范围，而“任何备份/上传均排除”的主张无法有界穷尽。项目采用显式 `RLIMIT_CORE=0`：持有秘密的项目子进程在exec前设置软硬限额为0，项目服务同时配置 `LimitCORE=0`。依赖绑定的Apport实现将有效limit=0传给rawcore写函数、该函数在创建/读取前早退，且所选同uid、`/home`下非打包可执行路径与默认unpackaged=false分支不生成report。适用性须按实际uid、路径、collector版本/配置和有效限额核查，不能把内核对pipe handler忽略RLIMIT的通则与Apport自己的早退混同。

验证使用无秘密、同uid、`/home`下被判非打包的合成可执行文件，分别取零和非零限额；只观察 `/var/crash` 与 `/var/lib/apport/coredump` 的新增成员/事件，不读内容。非零正对照未出现时不能推定零限额通过，也不自动重发；其他处理器、路径或配置不外推。

所有者接受Apport仍可能在root内存中读取过进程环境但不落盘的残余风险。此决定不宣称collector从未接触秘密，不选择全机分发器，也不以全局备份/上传排除为本路径前提。Apport版本/配置、实际限额、服务身份和分支漂移必须由后续doctor工程长期检查，漂移或无法核验时阻断对应准入；该长期工程不以本票验证替代。

代价是安全结论依赖明确collector行为与非打包分支，并需要持密进程全链和服务限额接线。相比全机分发器，作用范围保持项目内；相比不外流与事后清理，不要求持续证明所有备份/上传均不存在。其他文件/网络/进程隔离、认证与Live准入条件保持，各自验证；本决定不授予凭据/模型调用或产品激活许可。
